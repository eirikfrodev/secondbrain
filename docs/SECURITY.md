# Utsikt security assumptions

The full security model is in `docs/security/SECURITY_MODEL.md` and `HANDOFF.md`. This file records implementation-facing assumptions for the public web application.

- The browser is untrusted and receives no service-role key, provider refresh token, encryption key, provider credential, or unrestricted execution payload.
- Email, calendar, message, attachment, webpage, and model-composed content are untrusted data.
- Dynamic documents can select only registered block types and plain data. No generated HTML, JavaScript, CSS classes, SQL, shell, arbitrary URL fetch, or file write is executed.
- Browser APIs require authenticated workspace membership. MCP uses separate strong authentication. Personal and work workspaces are isolated.
- External actions require a current item revision, capability-specific Zod validation, source/account checks, idempotency, audit events, and explicit user approval where required.
- Irreversible communication is delayed locally before provider execution; Cancel is not described as recall. Undo is shown only when compensation is real.
- Mock mode is the default and performs no provider calls.
- Production deployment is not authorised by ordinary implementation work.

The Phase 2 baseline now enforces deny-by-default grants, workspace RLS, append-only history, requester-scoped cancellation, and capability/document constraints in the database. Revisit this model before Phase 4 credentials and external execution.

Phase 2 web clients use only the public Supabase URL and an `sb_publishable_` key; secret, service-role, and legacy JWT-shaped keys are rejected before browser compilation. Proxy owns session refresh, while a separate response-owning client handles login/logout cookie mutations; both preserve private/no-cache headers and neither is trusted as an authorization layer. Live persistence construction verifies authenticated audience, role, issuer, session ID, and user ID, and every database operation remains subject to grants and RLS. Mock mode never constructs a remote client, while incomplete or inconsistent live configuration fails closed. The service-role key is not read by the browser request path.

Google application sign-in is single-owner and identity-only. A private database row, configured out of band, admits one exact normalized Google email; an Auth hook rejects every other signup before creation, and a second database trigger rechecks admission before atomically binding the immutable Supabase UUID and provisioning owner membership. An empty configuration rejects all signups. The allowlist is unavailable to browser roles and the real address is not committed. Live product access requires a verified non-anonymous token whose immutable app metadata names Google, whose signed authentication-method reference includes OAuth, and whose UUID owns one RLS-visible personal workspace.

OAuth start, callback, and sign-out responses are private/no-store and preserve Supabase cookie headers. HTTPS session cookies explicitly use `Secure`; loopback HTTP is the only exception. Provider, scopes, callback path, and post-login destination are fixed by code. A bounded flow selector correlates each callback to its own PKCE verifier when several tabs are open. Callback input and the authoritative Google user are validated without reflecting provider errors or tokens, and the session is reconstructed so upstream Google provider tokens are absent before cookies are returned. Sign-out is POST-only, exact-origin checked, and local-session scoped. Login requests only `openid`, `email`, and `profile`; future Gmail/Calendar consent uses separate execution credentials and token storage.

Ask and queued-job cancellation use a stricter browser-mutation boundary than OAuth navigation. They require exact URL and `Origin` values plus `Sec-Fetch-Site: same-origin`, reject queries and encoded bodies, stream request bytes under a 16 KiB cap, validate strict Zod input before session/database construction, and derive user/workspace authority only from the verified request context. Responses are private/no-store, expose a reduced job receipt, and map persistence failures to fixed codes without serializing database causes. Item/job lookups collapse forbidden and missing results to the same route-specific `404`, reducing cross-workspace enumeration. Mock mutations return `404` outside loopback development/test and retain at most 256 process-local jobs, preventing an accidental preview/production mock endpoint or unbounded queue. These routes can queue or cancel internal AI jobs only; they cannot call a provider or execute model-composed code.
